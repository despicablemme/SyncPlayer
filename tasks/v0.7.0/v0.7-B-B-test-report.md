## §1 ffmpeg.wasm 命令与路径行为

- Loader 在首次 `getFfmpeg()` 时动态 import `@ffmpeg/ffmpeg` / `@ffmpeg/util`，把本地 `desktop/public/ffmpeg/ffmpeg-core.{js,wasm}` 转为 blob URL，再调用 `ffmpeg.load()`。
- 并发加载复用一个 promise；失败后清空 promise，后续可重试；取消后清空已终止 singleton。
- Probe 通过 `ffmpeg -hide_banner -i input` 收集 stream log，并以同一 callback identity 调用 `off('log', callback)`。
- H.264/H.265/HEVC/AV1 + AAC/AC3/Opus/Vorbis 走 copy；DTS 等不兼容组合抛 `SOFT_ENCODE_FALLBACK_UNSUPPORTED`。
- Copy 命令包含 `-map 0:v:0 -map 0:a:0? -c:v copy -c:a copy -movflags frag_keyframe+empty_moov+default_base_moof -f mp4`。
- 按 @ffmpeg/ffmpeg 0.12.15 API 检查 `exec()` 数字退出码；非 0 映射 `COPY_FAIL`。
- 输出必须在 byte 4 为 `ftyp`，否则映射为无效 fMP4 输出。

## §4 进度、错误与取消行为

- 进度：`onProgress({ percent })`，限制在 0–100。
- 取消：AbortSignal 触发后 `ffmpeg.terminate()` 恰好一次，reset singleton；终止后不再调用失效 worker 的 FS API。
- 正常清理：输入和输出虚拟文件均在 `finally` 删除。
- Listener 清理：probe log 与 transmux progress 均用原 callback 调用 `off()`；Abort listener 在 `finally` 移除。
- 2 GiB 限制：File/Blob 在读取 ArrayBuffer 前检查 `size`；二进制输入在写入前再次检查 byteLength。
- 并发：单例 FS 同时只允许一个 transmux job，避免文件/日志冲突。

## §5 阶段 B-C 准备

B-C 可从 `transmuxToFmp4(input, { onProgress, signal })` 获取 fMP4 `Uint8Array`，再由 MSE player 创建 SourceBuffer 并 append。当前 B-B 遵守边界，未修改 `app.js`、video-match、sync-engine，也未实际将输出喂入 video element。

B-C 接线前仍需验证 packaged Electron 中从 `file://` 读取 core blob URL 和 @ffmpeg wrapper worker 的实际行为；若失败，需要在 B-C/基础设施修正浏览器资源交付方式，而不是在本报告中当作已通过。

## §6 下一步建议

1. B-C 在 Electron renderer 中增加可观察的 loader/transmux smoke test，并记录真实 Worker/SAB 结果。
2. 主人样本 1.5G 接近 wasm32/renderer 全量 buffer 的实际边界；优先测 copy 路径峰值内存，失败时不要自动软编。
3. 当前任务按明确要求将软编 fallback 延后，DTS/不兼容编码返回可操作提示。
4. `@ffmpeg/core` GPL-2.0-or-later 与现有 Apache-2.0 发布策略仍需在 release 前明确处理。
5. 不运行自动 `npm audit fix`；依赖安全修复留待独立审查。
