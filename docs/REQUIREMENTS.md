## 一、项目概述

**项目名称：** SyncPlay  
**项目类型：** 同步播放工具 / 协作工具  
**一句话描述：** 两人异地同步播放视频，进度实时同步，延迟低  
**平台：** Web（浏览器，无需安装）  
**目标环境：** 任意网络环境（局域网 + 跨网段 + 公网，包括对称 NAT / 严格防火墙等不友好场景）

| R1 | **一键启动** | 双击 `start.sh` (Mac/Linux) 或 `start.bat` (Windows) 即可运行，无须任何手动配置 | ✅ `start.sh/command/bat` 已实现;**v0.4 Electron 桌面打包后改为双击 .dmg / .exe** |
| R2 | **启动后界面中配置房间** | 所有房间配置（创建/加入、房间号输入）都在 Web UI 中完成，不依赖命令行 | ✅ |

| R4 | **加入后自动构建同步链路** | 加入房间成功后自动建立 WebRTC P2P / TURN 中继连接，双方加载视频即同步 | ✅ TURN 路径验证通过 |

### v1.0 场景剧本

```
场景：异地异地两位好友一起看片
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

1. A 在 Mac 上双击 start.command
   - 服务自动起，浏览器自动开 http://localhost:8080/client/
   - A 选本地视频，点"创建房间"
   - 获得房间号如 "room-abc123"

2. A 把房间号发给 B（微信/QQ/手输）

3. B 在 Windows 上双击 start.bat
   - 服务自动起，浏览器自动开 http://localhost:8080/client/
   - B 选同一个视频，点"加入房间"，输入 room-abc123

4. 双方显示"已连接" → 自动同步
   - A 播放/暂停/seek → B 同步跟随
   - 双方看到一致的播放位置
```

## 二、核心功能需求

### 2.1 同步播放（核心）

| 需求描述 | 技术关键点 |
|----------|-----------|
| 两人播放同一视频时进度一致 | 进度同步协议 |
| 一方快进，另一方自动跳转 | seek 指令传递 |
| 一方暂停/播放，另一方同步 | play/pause 指令传递 |
| 同步延迟尽可能低 | WebRTC / 低延迟传输 |

---

## 三、系统架构

```
用户 A                   用户 B
  ↓                         ↓
本地视频文件 ←→ 浏览器 ←→ WebRTC DataChannel ←→ 浏览器 ←→ 本地视频文件
  ↓                         ↓
      ←←←←←←←← 信令服务器（仅建立连接）←←←←←←←←
```

**两条通道：**
1. **指令通道** — 传递 pause / seek / play 命令（WebRTC DataChannel）
2. **视频流** — 各自本地播放，视频文件不经过服务器

**注意：** MVP 阶段视频文件不走服务器，各自在本地播放。服务器只传指令。

## 四、技术选型

| 模块 | 技术选型 |

### 排除范围（暂不做）
- ❌ 视频流媒体传输（两端都播本地文件，不涉及网络传输视频）
- ❌ 用户列表、聊天等社交功能
- ❌ 用户注册、登录、密码、邮箱、手机号
- ❌ 房间密码/链接有效期/角色权限

---

### 同步原理

1. A 点击播放 → 发送 `{"type": "play", "position": 12.5}` 到 B
2. B 收到 → 立即将 video.currentTime 设为 12.5 并播放
3. A 拖动进度条 → 发送 `{"type": "seek", "position": 45.0}` 到 B
4. B 收到 → 立即将 video.currentTime 设为 45.0

**延迟目标：** < 200ms

## 八、v0.6 新增需求 (2026-06-09 立项)

### FR-1: 房间生命周期 — 退出 + 换房

**背景**: 现在只能创建/加入房间, 没法退出. 看完一个视频想换房必须刷新页面.

**功能需求**:
- **退出当前房间**: UI 加"退出"按钮, 点了:
  - 关闭 WebRTC 连接 (`peer.destroy()` 或类似)
  - 关闭 PeerJS connection
  - 回到主界面 (无房间状态)
  - **不**刷新页面
- **重新加入另一房间**: 退出后 UI 自动展示"加入房间"输入框, 用户输入新房间号 → 加入
- **状态机扩展**: 房间状态机加 `in_room` / `connecting` / `disconnected` / `no_room` 四态

**验收标准**:
- [ ] 创建房间后, 能点"退出"回到主界面
- [ ] 加入房间后, 能点"退出"回到主界面
- [ ] 退出后能输入新房间号立即加入 (不刷新页面)
- [ ] 退出后 peer connection 正确关闭 (无 console 错误)
- [ ] 退出后再创建/加入, 功能正常

**非目标** (本期不做):
- ❌ 房间历史记录
- ❌ 最近房间列表
- ❌ 房间密码

---

### FR-2: 视频 URL 加载 bug 修复

**背景**: 用户输入视频 URL (http://..., https://...), `<video>` 标签加载会失败.

**功能需求**:
- 修这个 bug, 让 URL 加载能成功
- 覆盖场景: 本地文件 (`file://`) / HTTP URL / HTTPS URL / 跨域 URL / 常见视频格式 (mp4, webm, m3u8)

**可能根因** (Builder 接手时排查):
- CORS 限制 (跨域)
- Mixed content (https 页加载 http 视频)
- `load()` 调用时机 (应该在 `src` 设置之后立即调用)
- MIME type 缺失 (服务端没返回正确 content-type)
- 短链/重定向

**验收标准**:
- [ ] HTTP URL 能正常播放
- [ ] HTTPS URL 能正常播放
- [ ] 跨域 URL (CORS 允许) 能正常播放
- [ ] m3u8 / hls 流能正常播放 (如支持)
- [ ] URL 加载失败时, UI 给清晰错误提示 (不是黑屏)
- [ ] URL 加载成功后, 视频元数据 (时长/尺寸) 能正确读取

---

### FR-3: 解耦视频加载与房间 + 视频不匹配提示

**背景**: 现在必须**先**加载视频才能进房间. 体验不好 — 用户可能想"先进房再看片"或"看完这个再换一个".

**功能需求**:
- 房间生命周期 (创建/进入/退出) **完全独立**于视频加载
- 任意顺序都行: 加载视频 → 进房 / 进房 → 加载视频 / 加载视频 → 进房 → 退房 → 进新房 ...
- **新功能**: 两端都加载视频后, 自动校验视频信息是否匹配:
  - **匹配** = URL 相同 / 文件名相同 / 时长差 < 1s (任一即可, 由 Builder 决定具体策略)
  - **不匹配** = UI 状态区显示提示: **"视频不匹配, 无法同步进度"** (用红色/警告色)

**新 UI 状态**:
| 状态 | 描述 | 状态区显示 |
|---|---|---|
| 未进房 | 用户在主界面 | "请创建或加入房间" |
| 进房中 | WebRTC 连接中 | "连接中..." |
| 已连接, 视频未加载 | 两端都连上, 没人加载视频 | "已连接, 请加载视频" |
| 已连接, 仅 A 加载 | 只有 A 加载了视频 | "等待对方加载视频..." |
| 已连接, 双方加载, 匹配 | 正常状态 | (无提示, 视频正常同步) |
| 已连接, 双方加载, **不匹配** | 🆕 新状态 | **"视频不匹配, 无法同步进度"** (红色警告) |
| 已连接, 一方退房 | B 退房后 A 看到的 | "对方已退出房间" |

**验收标准**:
- [ ] 加载视频前能创建/进入房间
- [ ] 进房前能加载视频
- [ ] 视频不匹配时状态区显示红色提示
- [ ] 视频匹配时无提示, 正常同步
- [ ] 状态切换平滑, 无闪烁/卡顿
- [ ] 单元测试覆盖房间状态机 + 视频匹配逻辑

**视频匹配算法** (建议, Builder 可调整):
```javascript
function videosMatch(a, b) {
  if (!a || !b) return false;  // 任何一方没加载 = 不算匹配
  if (a.url && b.url) return a.url === b.url;  // URL 相同
  if (a.fileName && b.fileName) return a.fileName === b.fileName;  // 文件名相同
  if (a.duration && b.duration) return Math.abs(a.duration - b.duration) < 1;  // 时长差 < 1s
  return false;
}
```

### 跨需求: 状态机重构建议

FR-1 + FR-3 都需要改房间状态机. 建议**一次性重构**成:

```
状态: no_room → connecting → in_room_no_video → in_room_waiting_peer_video → in_room_synced → in_room_mismatch
                                                  ↓
                                            disconnected (peer lost)
                                                  ↓
                                              no_room (退出)
```

主 agent 建议: 阶段 B 拆任务时, FR-1 + FR-3 状态机部分**合并**成一个子任务, 避免重复改状态机.
